# Local physical implementation addendum

FW-DB-LOCAL-FOUNDATION-001 · 09/10/2026 · target remains FW-PHYS-T1-ASYNC-005.

This version records implementation corrections found while executing PostgreSQL 16. The pinned API005, DB005 model, native003 and original architecture bundles are unchanged. It is an explicit physical deployment overlay, not a replacement target revision or a declaration that DB005 is implemented.

1. **Migration journal placement.** DB005 lists a logical `migration_journal` among its 87 tables, while Operations describes its journal as infrastructure outside “87 domain tables.” These counts describe conflicting inventories. The local implementation maps that same logical journal to `fw_infra.migration_journal` and keeps all eight planned fields (`id`, `created_at`, `migration_name`, `checksum`, `schema_from`, `schema_to`, `applied_at`, `runner_version`). It adds `release_id` and `catalog_sha256`. There is one authority, with no duplicate domain journal. At full model parity, the pinned list means 86 domain tables plus this infrastructure journal; any additional phase/progress infrastructure must be inventoried separately. Current execution has **54 domain tables plus one infrastructure journal**. The remaining model tables and fields are required, not discarded.
2. **Integer numeric inputs.** Historical `numeric(18,0)` coerces `1.5` to `2` before a CHECK or trigger can see the original value. Migration004 changes each inherited `numeric(18,0)` column to unconstrained `numeric` with an explicit finite/integer/18-digit bound, retaining existing sign/null constraints. This is a intentional physical type deviation from the pinned model, with the same externally specified 18-digit integer money domain. SQL now rejects fractions, NaN, infinity and overflow; TypeScript separately rejects numbers, exponent notation, separators, padding and negative zero before casting. SQL cannot validate an input's original string notation after casting; that lexical responsibility remains at the API/Engine boundary. Quantity/price `numeric(28,8)` SQL hardening and full API DTO wiring remain required.
3. **Committed ledger seal.** Historical deferred balance checking allows a balanced append to an already committed group. Migration004 backfills valid legacy groups as sealed without altering money. Invalid legacy groups stop migration for quarantine. New groups must begin building and seal inside the same transaction; inserts lock the workspace anchor and group before testing seal state. Sealed groups reject append/update/delete; posting lines reject update/delete/truncate. Reversal requires an exact multiset of opposite lines, beyond equal aggregates. Used ledger-account identity/kind cannot be retargeted and internal purpose is unique per workspace.

The implementation deliberately replaces only the historical entry-group immutability trigger, then restores stronger lifecycle guards. Historical migrations, seed and evidence are not rewritten. Application code must explicitly seal newly constructed groups; the old seed is only run before upgrade. Opening declarations are preserved and not reposted. This is a deploy-order change for future Ledger service integration, not an adapter/UI change.

The runner only accepts managed disposable `fw_synthetic_*` databases on PostgreSQL16/UTF8 and never silently adopts an unknown namespace. Each journal insert and DDL phase commit together. A killed connection stops execution; retry starts from durable journal/catalog state. Destructive down migrations and nontransactional index creation are unsupported and rejected.

This addendum resolves placement/precision/seal decisions for local implementation. Full tenant/auth/service grants, security procedures, J2 cutover, financial workflows, all DB005 fields/FKs, encrypted backup, independent witness and restore still require implementation and runtime tests. Foundation read-role tests do not prove complete T1 runtime authority isolation.
